repo-operator

Cloud Computing
Hermetic Builds
Makefile

A Make library that provides hermetic, containerised, and parameterised build operations as a versioned dependency shared across repositories.

Published

October 30, 2024

Modified

September 24, 2026

repo-operator is a Make library that provides a single, versioned set of targets for operating a collection of repositories: container images, Go, Helm charts, changelogs, and repository hygiene. Targets execute their tooling in containers pinned by content digest, and consumer repositories incorporate the library as a Git submodule.

Background

The name and design draw on two concepts from mathematics and physics.

Hermitian operators. In quantum mechanics, observables are represented by Hermitian operators, whose eigenvalues are real, so every measurement yields a well-defined value. The name plays on hermetic builds, a principle of release engineering in which a target is a pure function of its declared inputs and produces the same output regardless of who runs it, where, or when.

Non-locality. A non-local operator determines its value at a point from a function over its entire domain, rather than from that point’s neighbourhood. Likewise, a target’s behaviour in a repository is determined not by that repository’s Makefile or host, but by a single shared definition.

Motivation

Software projects accumulate a common layer of build and operational logic. When each repository maintains this layer independently, the implementations diverge, and their behaviour becomes coupled to the tool versions installed on individual machines. A correction to a security scan must then be repeated in every repository, and repositories that are updated less often continue to run outdated toolchains without any visible failure.

repo-operator treats this layer as a versioned dependency. A change is made once, in the library, and each consumer adopts it by advancing its submodule reference on its own schedule.

Design

  • Hermeticity. Tools run in containers pinned by sha256 digest, so local and CI executions use identical tool versions. The exceptions are op-go-build and op-go-mod-* (host Go), op-precommit-install (host pre-commit), and op-image-build (host buildx). The outputs are tool-deterministic rather than bit-for-bit reproducible, since the containers reach the network and artefacts carry the commit and build time.
  • Targets as functions. Targets take parameters at invocation, such as make op-image-build IMAGE_NAME=my-app, so one target serves every image and every repository.
  • Naming. Targets are named op-<domain>[-<action>] after their module, and private variables carry the OP_ prefix. Public parameters are unprefixed and declared with ?=, so a value from the consumer Makefile, the command line, or the environment takes precedence over the default.
  • Self-documentation. make op-help renders every target and public parameter, with its declared default, from ##v and ##p annotations kept next to the definitions.

Usage

The host requires docker with buildx, make, and git. Add the library as a submodule, conventionally under build/:

git submodule add https://github.com/ioaiaaii/repo-operator.git build/repo-operator

Then set parameters, include the library, and define targets in terms of its interface. all.mk includes every module; a subset starts with core.mk.

OPERATOR_PATH  := build/repo-operator
VERSION_PKG    := github.com/myorg/my-service/pkg/version

include $(OPERATOR_PATH)/makefiles/all.mk

help: op-help

##@ App

.PHONY: app-image
app-image: ## Build the application image.
    @$(MAKE) --no-print-directory op-image-build IMAGE_NAME=my-app

A complete example is in examples/basic.

Extending

Public parameters are overridden in the consumer Makefile before the include, or at invocation, because several are expanded when the library is parsed. LD_FLAGS is the exception and can be overridden only at invocation or after the include.

make op-image-build IMAGE_NAME=my-app IMAGE_TAG=dev

Consumer targets annotated with ##, grouped under ##@ sections, appear in make op-help alongside the library targets. A recipe can enforce its own parameters with $(call require,NAME), which stops with the name of the missing parameter:

##@ Database

.PHONY: db-migrate
db-migrate: ## Run database migrations.
    $(call require,DB_URL)
    ./scripts/migrate.sh

Versioning

Consumers pin the submodule to a release, and an upgrade is committed in the parent repository:

git -C build/repo-operator checkout v1.2.0
git add build/repo-operator && git commit -m "chore: pin repo-operator to v1.2.0"

Reference

The tables list required parameters and those that change behaviour; make op-help lists all of them. <repo> denotes the name of the directory in which make runs.

Core

Target Description
op-help List every target and public parameter
op-env Print the resolved tag, branch, version, and commit
Parameter Description
OPERATOR_PATH Path from the repository root to the submodule. Default: .
SRC Go source root. Default: .
BUILD_PATH Build tree containing ci/ and package/. Default: build
DEPLOY_PATH Chart tree. Default: deploy
DEFAULT_BRANCH Release branch, for tag detection and commit linting. Default: master
VERSION Version for image tags and binary stamps. Default: the branch name, or on a detached HEAD the vX.Y.Z tag at the tip of DEFAULT_BRANCH

Go

Target Description
op-go-lint Run golangci-lint with $(BUILD_PATH)/ci/.golangci.yml (v2 schema)
op-go-test Run go test ./...
op-go-build Build a static binary, using the host Go toolchain
op-go-mod-update Update dependencies, then run go vet
op-go-mod-sync Run go mod tidy, vendor, and verify
Parameter Description
CMD_PATH Main package sources, relative to SRC. Default: cmd/<repo>/*.go
BINARY_PATH Output binary. Default: $(BUILD_PATH)/<repo>
GOOS, GOARCH Target platform. Default: linux, amd64
VERSION_PKG Package declaring BuildVersion, BuildHash, and BuildTime, stamped at link time. A wrong path yields an unstamped binary without an error

Image

Target Description
op-image-lint Lint the Dockerfile with hadolint
op-image-build Build the image, or build and push it with IMAGE_MODE=publish
op-image-digest Print the digest recorded by the last build
op-image-run Run the image as the container IMAGE_NAME, publishing its exposed ports
op-image-inspect Analyse layer efficiency with dive
Mode Platforms Output Attestations
local (default) Host architecture Loaded into the daemon None
publish linux/amd64, linux/arm64 Pushed to the registry Provenance and SBOM

publish requires a docker-container builder with QEMU (docker buildx create --use).

Parameter Description
IMAGE_NAME Required. Image name. The Dockerfile defaults to $(BUILD_PATH)/package/<IMAGE_NAME>/Dockerfile
IMAGE_REPO Registry and namespace, e.g. ghcr.io/myorg, or a Docker Hub account name. Required for publish
IMAGE_TAG Default: VERSION with characters outside [A-Za-z0-9.] replaced by -
IMAGE_EXTRA_TAGS Additional --tag flags, e.g. --tag ghcr.io/myorg/app:latest
IMAGE_BUILD_ARGS --build-arg flags. The default passes LD_FLAGS, which an override must repeat

Scan

op-scan runs Trivy with the subcommand in TRIVY_ARGS. The cache must lie inside the mounted SRC, and images are scanned from a docker save archive:

make op-scan TRIVY_ARGS="fs --cache-dir build/ci/.cache/trivy --exit-code 1 --severity HIGH,CRITICAL ."

Chart

Changelog

Target Description
op-changelog-lint Lint commits from origin/<DEFAULT_BRANCH> to HEAD with commitlint
op-changelog Lint, then generate CHANGELOG.md with git-chglog
op-changelog-release Generate release notes for the required TAG

Configurations are read from build/changelog/. The library’s own directory, including its two templates, serves as a starting point once repository_url is changed.

OpenAPI and OpenTelemetry

Target Description
op-openapi-docs Render the required OPENAPI_FILE as Markdown into the required OPENAPI_DOCS_PATH

Repository Hygiene

Target Description
op-gitignore-sync Append the Go, macOS, and Terragrunt templates to .gitignore
op-precommit-sync Append the base, helm, and terragrunt hook configurations to .pre-commit-config.yaml
op-precommit-install Sync, then run pre-commit install on the host

Both syncs append template lines without parsing the destination file, so they are run once, when a repository adopts the library.
